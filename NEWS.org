*[Released]*

** v1.3.1 (2026-11-05)

A repair release: a suite reports its children in declaration order again, so two
runs of one suite write the same JUnit document, and the README stops carrying
release notes of its own.

*** Fixes

- A suite reported its children in completion order.  They run in fibers and
  =evaluate-thunks-concurrently= collected them as they reported back, so a
  nested suite could sit inside or after its siblings from one run to the next
  and two runs of one suite wrote different JUnit documents - the determinism
  test caught it on CI.  The evaluator carries each answer's position through
  the channel and sorts on it, so every consumer sees declaration order.
- The new case in =test/veritas/unit/determinism.scm= drives that race with a
  channel handshake between two children instead of a sleep, so it fails on the
  old order without depending on the machine.

*** Documentation

- The README no longer keeps a *What changed in 1.0* list.  Release notes belong
  in this file, and the five points it made are recorded under v1.0.0 below: the
  shuffle default and its replayable seed, =(lazy ...)=, the file carried by
  every test result, the measured speedup, and the split into =docs/=.  The
  README says where the notes live instead.

*** Packaging

- The version is 1.3.1 everywhere it is named, and the Arch recipe verifies the
  archive the tag serves.

*[Released]*

** v1.3.0 (2026-11-05)

A release about the agent instructions and the move to GitHub: =maak agents=
writes AGENTS.md from two pinned skills and the practices kept in the build
file, and every recipe names the repository's new home.

*** Build

- =maak agents= regenerates =AGENTS.md= from the skills pinned in =maak.scm=:
  it downloads =ponytail= and =test-driven-development= at their commits, then
  appends the practices from the same file.  The fetch needs nothing but curl
  and the output is deterministic, so a copied task writes the same document
  byte for byte.
- A skill is imported whole.  Picking sections out of one needs heading
  detection, and a line-based scan cannot tell a heading from a =##= line
  inside a code fence.
- The generated practices name no project path, module or task, so another
  repository copies the section and replaces only the data.

*** Packaging

- The recipes, the container image metadata and the package homepages point at
  https://github.com/jjba23/veritas now that Codeberg is archived, and the Arch
  recipe verifies the release archive it fetches.

*** Documentation

- The README says where =AGENTS.md= comes from and that the task is the recipe
  for another repository.

** v1.2.0 (2026-11-05)

The release that changes the licence, the pipeline and the guide: veritas is MIT
licensed, CI/CD runs on GitHub Actions, and rerunning what failed is documented
and fixed on Guile 3.0.10.

*** License

- veritas is MIT licensed.  =LICENSE= replaces =COPYING=, every source header
  states =SPDX-License-Identifier: MIT=, and the packaging recipes, the container
  image labels and the manual page name the new licence.

*** CI/CD

- The pipeline moved from Woodpecker to GitHub Actions.  =.github/workflows/
  ci.yml= hands Byggsteg the two maak tasks the Woodpecker configuration
  submitted - =maak-test= on a push to =trunk=, then =maak-deploy= - and
  =.woodpecker/= is gone.
- =tests.yml= keeps its job of validating the JUnit document against the schema,
  and its header no longer describes GitHub as a mirror.

*** Fixes

- The rerun tests built their fixtures through the keyword arguments of
  =make-pre-test-result= without passing any of them.  Guile 3.0.10 inlines calls
  to keyword-argument procedures, and that call allocated the record with the
  wrong field count, so =rerun.scm= failed on a Guile 3.0.10 machine while
  passing on 3.0.9 and 3.0.11.  The fixtures now use the positional constructor,
  =make-raw-pre-test-result=, which is exported for anyone building a result
  tree by hand.

*** Documentation

- [[file:docs/running.org][Running tests]] has a *Rerunning only what failed* section: the record every
  run writes, why an empty record selects nothing, the =#all= marker, and what a
  parallel run records.
- The environment table in [[file:docs/getting-started.org][Getting started]] lists every variable the runner
  reads, including =VERITAS_JOBS=, =VERITAS_PARTITION= and =VERITAS_ONLY_FAILED=.
- [[file:docs/reporting.org][Reports and diagnostics]] says what a run leaves in =reports/= and which
  variable moves each file.
- The README shows the rerun command and names the pipeline.

** v1.1.1 (2026-11-04)

A repair release: the coverage suite runs again, and flakiness reaches CI.

*** Fixes

- `coverage.scm` compiled and loaded a fixture module without saving the module
  excursion.  Loading it left the loader's current module set to the fixture, so
  every `suite` form after that line was evaluated there and the whole file
  raised `Unbound variable: suite`.  The load is wrapped now and the file's
  suites run.

*** Improvements

- `log-flaky` is a reporter level of its own: the JSON reporter emits
  `{"level":"flaky",...}` instead of an informational line, and the GitHub step
  summary has a `flaky` column.
- A test that names a data file (`"data/passwords.txt"`) is selected when that
  file changes, so a change outside `src` still runs the test that needs it.

** v1.1.0 (2026-11-04)

A release about the edit loop: run only what a change can reach, retry what
fails intermittently without hiding it, and keep a step-by-step trace of the run
that can be read afterwards.

** Change-aware runs

- `veritas --changed` (or `VERITAS_CHANGED=true`) runs only the test files the
  working tree change can reach, and `--since REF` does the same against a
  branch's base.  The selection follows `#:use-module` forms from the sources
  under `VERITAS_SRC_DIR` (default `src`) to their importers, then to the test
  files that import them; a changed test file and a test named after a changed
  file are selected too.  A change that touches nothing runs everything, so a
  filtered run is never silently empty.
- The graph is a module of its own, `(veritas impact)`: `module-name-of-file`,
  `module-imports`, `git-changed-files`, `affected-test-files` and
  `changed-selection` answer the same questions from a script.
- `--list` (`VERITAS_LIST=true`) prints the files a run would run, one per line,
  and runs none of them, so a CI job can inspect a selection before trusting it.

** Retries for intermittent failures

- `#:retries N` on a `test` reruns it, hooks included, up to N extra attempts;
  `veritas-retries` and `VERITAS_RETRIES` (`--retries N`) set the default for a
  run.
- A test that fails and then passes is reported as flaky with its attempt count:
  `attempts` is a slot of `pre-test-result`, so a report can tell an
  intermittent hiccup from a real failure instead of hiding either.
- Flakiness is counted apart from passes: the run's totals end with `N flaky
  tests`, and the JUnit `testcase` carries `flaky="true"`.

** Traces

- `--trace` (`VERITAS_TRACE=true`) records every step of a run - test start,
  each assertion's verdict, test end with its attempt count - to
  `reports/traces/last.scm` as plain s-expressions, and `--show-trace` prints it
  as a numbered timeline.
- `(veritas trace)` exposes the recorder: `veritas-tracing?`,
  `veritas-trace-frames`, `trace-event!`, `write-trace!`, `read-trace`,
  `render-trace` and `show-last-trace`.
- The timeline records suites as well as tests: `suite-start` and `suite-end`
  frames show the nesting and how many tests a suite held.

** One import

- `(veritas all)` re-exports the runner, the assertion library, the doubles,
  snapshots, table and generated cases, and the BDD aliases, so a test file needs
  one import instead of five.  The module is generated from the other modules'
  export lists and cannot drift from them.

** Documentation

- `docs/incremental.org`, `docs/debugging.org` and `docs/batteries.org` are new,
  and the README, the documentation index and the getting-started environment
  table point at them.
- `--changed`, `--since`, `--src-dir`, `--retries`, `--trace`, `--no-trace` and
  `--show-trace` are in `veritas --help` and the man page.

** v1.0.0 (2026-11-04)

A quality pass over the framework: assertions defer work without `eval`,
ordering is deterministic where it can be, failures name the file they came
from, the hot paths are measured, and the guide lives in `docs/`.

*** Lazy assertions

- An assertion evaluates its payload when it runs, in the scope where it was
  written: `(assert-equal #:expect 2 #:got (lazy (+ 1 1)))`.  `lazy` is a small
  record holding a thunk, forced afresh by each assertion that receives it, so
  nothing is cached behind your back; it runs inside the assertion's `#:timeout`,
  which is what lets a deadline interrupt it.  `#:expect` accepts it too.
- This replaces the quoted `(comp ...)`, `(compute ...)` and `(computare ...)`
  lists, which were evaluated with `eval` in the interaction environment: they
  lost the lexical scope around the expression and compiled it at run time.

*** Breaking

- `(comp ...)`, `(compute ...)` and `(computare ...)` are removed; wrap the
  expression in `(lazy ...)`.
- `pre-test-result` gained a `line` slot beside `file`, and
  `make-pre-test-result` accepts `#:line`.
- Suite shuffling is unchanged: still the default, still seeded, still
  replayable with `VERITAS_SEED`.

*** Determinism

- Files are sorted by path, results are collected in declaration order even when
  a suite runs concurrently, and JUnit classes are written in first-seen order
  with their cases in declaration order.
- The JUnit grouping is one pass over the cases instead of a scan per class.
- The wall clock and the running test's location are parameters
  (`veritas-clock`, `veritas-current-location`), so a test can pin them and two
  runs can be compared byte for byte.
- New tests: `test/veritas/unit/determinism.scm`.

*** Source references

- `test` and `suite` capture their declaration site; every test result records
  the file it came from, and JUnit writes `file` (plus `line` when a caller
  supplies one).  Guile 3.0 exposes no line for a syntax object, so files are
  automatic and lines are opt-in.
- New tests: `test/veritas/unit/references.scm`.

*** Performance

- A test's captured-output port is opened when the test runs, not when it is
  declared; the reporter is called directly instead of through `apply` on a
  one-element list; XML escaping copies runs of ordinary characters as one
  substring.
- New benchmark: `bench/bench.scm`, with `BENCH_CASES` for larger trees.
  Measured against v0.11.0 on Guile 3.0, single core:

  | Path                      | v0.11.0  | v1.0.0   |
  |---------------------------+----------+----------|
  | declare a test            | 2.57 µs  | 2.46 µs  |
  | run one assertion         | 14.58 µs | 12.91 µs |
  | JUnit data, 5000 cases    | 388.7 ms | 383.9 ms |
  | result counts, 5000 cases | 26.4 ms  | 26.5 ms  |

  Assertion execution is about 11% faster; report generation is dominated by
  formatting each attribute and is unchanged within noise.

*** Documentation

- The README is a landing page; the guide is seven documents under `docs/`
  (index, getting started, writing tests, running tests, reports and
  diagnostics, internals, migration), each with a table of contents, a link
  back to the README and links to related topics.
- The lazy model, the determinism guarantees and the two seams are written down
  and covered by tests.

** v0.11.0 (2026-11-04)

The reports now carry what a consumer outside the terminal needs, and there is a
reporter for GitHub Actions.

*** Report data

- Every test result records the file it came from and how long it took.  The
  JUnit document writes both out: a ~testcase~ carries ~classname~ (the file,
  from the project root), ~file~, ~suite~ (the path through the suites) and its
  own ~time~, and each ~testsuite~ sums the durations of its cases.  That is what
  IntelliJ shows as durations and what a CI action uses to attach a failure to a
  file.
- Line numbers are not written: Guile gives no reliable line for an interpreted
  test, and a wrong line is worse than none.
- A raised task is now written as one ~error~ element.  The failure data for it
  was shaped as two half-entries, so writing the document for a run with a
  raising task failed outright.

*** github-reporter

- ~VERITAS_REPORTER=github-reporter~ writes
  ~::error file=...,title=...::message~ annotations for the failures of each file
  - the first ten, which is GitHub's per-step limit, plus a notice naming how
  many more the JUnit document holds - and appends a row per file to
  ~$GITHUB_STEP_SUMMARY~.  The log stays quiet; outside a workflow the same
  setting reads like ~monotone-reporter~, so it is never a switch that silently
  hides a local run.

*** Keeping it true

- ~test/veritas/junit.xsd~ is the schema of the document, and
  ~.github/workflows/tests.yml~ validates the report of the project's own run
  against it before ~mikepenz/action-junit-report~ publishes it.
- ~test/veritas/unit/jobs.scm~ compares a whole document - files, durations,
  escaping, counts and header - against an expected one, and checks the
  annotation line and the summary row.

** v0.10.1 (2026-11-03)

A single-process run keeps going after a failing file.  ~veritas-run~ reports a
failing file by exiting 1, which used to end the whole run there: the files
scheduled after it never ran, and the global totals were never printed -
precisely when a run is failing and the numbers matter.

*** Fixes

- The file loop catches that exit, and an error raised while a file loads, names
  the file and carries on, then reports the failures together and exits 1 once
  every file has had its turn.  Single-process runs now behave the way ~--jobs~
  already did; ~run-test-files~ and ~run-test-file-guarded~ in
  ~(veritas runner)~ are the two procedures that do it.
- ~test/veritas/unit/jobs.scm~ gains probe files that pass, exit and raise, and
  checks that a file which exits or raises is reported rather than ending the
  run, and that the file after it still runs.

** v0.10.0 (2026-11-03)

A run now ends with its totals.  One line says how many test files ran and how
many suites, tests and assertions they held between them, whether the files ran
in one process or across the workers of ~--jobs~.

*** Global counts

- Every ~veritas-run~ reads the numbers off its own result tree - the same tree
  the report is printed from, so the two cannot disagree - and adds them to the
  tally of the process.
- The runner prints one ~global totals~ line at the end of the run: the files,
  suites, tests and assertions of every file added up.  With ~--jobs~ each
  worker leaves its counts for the parent, which merges them the way it already
  merges the record of failures, the JUnit reports and the coverage fragments.
- A benchmark measures instead of asserting, and a task that raised is reported
  as an error, so neither is counted as a test or an assertion of its own.
- New in ~(veritas prelude)~: ~empty-result-counts~, ~add-result-counts~,
  ~result-counts~ and ~result-counts-summary~.  New in ~(veritas veritas)~: the
  ~veritas-result-counts~ tally, plus ~write-result-counts~ and
  ~read-result-counts~, which are how a worker hands its numbers over.
- ~test/veritas/unit/counts.scm~ checks the counts of a nested tree, the file
  count, what a benchmark and a raising task contribute, the summary line and
  the round trip through a file.

** v0.9.0 (2026-10-26)

Coverage is the release.  A run now switches Guile's VM to the engine that
counts instructions for the measured part, so the reports carry real numbers
instead of a page of zeroes, and it writes them in every shape a dashboard
reads: LCOV, JSON, Cobertura, JaCoCo and one self-contained HTML page for the
whole project.  Two bugs found on the way - a suite hiding a child that raised,
and helpers losing their bracket when a test yielded - are fixed too.

*** Code coverage that works

- Coverage used to write reports whose every line had a count of zero: Guile
  fires the counting hook only on its debugging VM, and the run never switched
  engines.  The measured part of a run now happens on that engine, and the
  engine found before it is put back afterwards.
- Coverage is asked for with ~#:with-coverage? #t~ on ~veritas-run~, or once for
  a whole run with ~VERITAS_COVERAGE=true~, which measures every test file the
  runner loads rather than only the files that ask.  ~VERITAS_COVERAGE=false~
  (or ~--no-coverage~) is the opposite and wins over a file that asks for it,
  which is what makes a quick run quick.
- The project's own ~maak test~ task measures coverage by default; ~maak
  test-fast~ runs the same suite with measurement refused.
- The reports of a run are merged instead of overwritten: one LCOV trace file
  (~reports/lcov/veritas.info~), one JSON summary
  (~reports/lcov/coverage-summary.json~), a Cobertura document
  (~reports/lcov/cobertura.xml~), a JaCoCo document
  (~reports/lcov/jacoco.xml~) and an HTML report
  (~reports/html/index.html~).  With ~--jobs~ the fragments of every worker are
  merged into the same report.
- The HTML report is now *one page* that holds the whole project: the summary,
  a filterable table of files and the annotated source of every file, with a
  switch that hides covered lines.  It needs no other tool and opens from a
  ~file://~ URL.
- Cobertura and JaCoCo are written for the Java-world dashboards: SonarQube,
  Jenkins, GitLab, Azure DevOps and IDE coverage gutters read them.  The source
  roots of the run are named and the files are reported relative to them.
  ~VERITAS_COBERTURA_PATH~ and ~VERITAS_JACOCO_PATH~ move the documents.
- ~#:coverage-dir~, ~#:coverage-html-dir~, ~#:coverage-include~ and
  ~#:coverage-exclude~ (or ~VERITAS_COVERAGE_DIR~, ~VERITAS_COVERAGE_HTML_DIR~,
  ~VERITAS_COVERAGE_INCLUDE~, ~VERITAS_COVERAGE_EXCLUDE~, or the ~--coverage-*~
  flags) say where the reports go and which sources they cover.  By default only
  the current directory is measured, which keeps Guile and the dependencies out
  of the report; a run that measured nothing now says so instead of passing
  silently.
- Benchmarks run outside the measured extent, so the per-instruction hook does
  not distort a measurement about timing.
- New ~(veritas coverage)~ module: ~collect-coverage~, ~coverage-report-files~,
  ~coverage-report-percentage~, ~write-lcov-file~, ~read-lcov-file~,
  ~merge-coverage-reports~, ~merge-lcov-files~, ~write-html-report~,
  ~write-coverage-json~, ~write-cobertura-xml~, ~write-jacoco-xml~,
  ~publish-coverage!~ and ~regenerate-coverage-reports~.
- ~test/veritas/unit/coverage.scm~ compiles a fixture module and checks the
  counts, the include filter, the LCOV round trip, the merge, the Cobertura and
  JaCoCo documents, the all-in-one HTML page, the JSON summary and a full
  ~veritas-run~ with coverage.

*** Fixes

- A test whose thunk raised inside a suite is now reported: the exception
  arrives as a string, and the report used to drop a string child of a suite
  without a word, which made a failed suite look empty.
- ~with-container~ and ~with-temporary-binding~ keep their bracket across a
  fiber suspension.  Fibers unwinds a plain ~dynamic-wind~ whenever a task
  yields - a ~sleep~ or a port operation is enough - so the container was
  removed, or the binding put back, in the middle of the thunk.  Both now use
  ~dynamic-wind*~ from ~(fibers scheduler)~ when it is there, with the old
  behaviour as a fallback; ~call-with-fiber-safe-wind~ in ~(veritas prelude)~ is
  the shared helper, and the coverage engine switch uses it too.
- ~test/veritas/unit/container.scm~ gains a test that a yielding thunk keeps its
  container until it is done, and installs its fake runtime with ~chmod~ instead
  of ~(system* "chmod" ...)~: spawning a process while a module is being loaded
  deadlocks on some Guile builds.
